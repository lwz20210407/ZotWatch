## 1. 这个项目是什么

每周一次，从用户的 Zotero 文库（4399 篇）学出研究兴趣画像，去 OpenAlex / Crossref
抓最近 30 天的新论文，按"与本人研究链的相关度"排序，产出**一个网页周报 + 一封邮件
简报**，跑在 GitHub Actions 上，无服务器、无数据库。

用户是 CS/力学方向的博士生。**他的研究链是全系统唯一的判据**，下面反复出现：

```
材料 (LPBF/SLM 制备的 TC4 / Ti-6Al-4V)
  → 载荷条件 (温度 / 应变率 / 复杂应力状态；三者独立，不总是耦合)
  → 现象 (塑性变形 / 延性断裂 / 损伤演化)
  → 模型 (本构与失效模型的建立与标定)
  → 实现 (UMAT/VUMAT, LS-DYNA/Abaqus)
  → 验证 (冲击侵彻试验)
```

明确**不属于**本课题（用户两次主动纠正，都是在看完推送之后）：
陶瓷复合装甲；材料微观表征（EBSD/TEM 这类以表征手段本身为研究对象的工作）。

## 2. 起点：上游 `Yorks0n/ZotWatch`

### 2.1 严格说这不是 GitHub fork

用户没点 Fork 按钮，而是新建仓库把上游代码拷了进来，所以 GitHub API 报
`isFork: false, parent: null`。上游是 **[`Yorks0n/ZotWatch`](https://github.com/Yorks0n/ZotWatch)**
（README 里自称 ZotWatcher），MIT 许可。首个提交 `875591d`，2026-04-23，39 个文件。

### 2.2 上游原版做了什么

按上游 README 的原话：

- **Zotero 同步**：通过 Zotero **Web API** 获取文库条目，增量更新本地画像。
- **画像构建**：对条目向量化，提取高频作者/期刊，记录近期热门期刊。
- **候选抓取**：优先通过统一的 **Supabase Edge Functions** 公共候选池，并对个人
  热门期刊做额外精准抓取（Crossref）。
- **去重打分**：语义相似度 + 时间衰减 + 引用/Altmetric + SJR + 白名单加分。
- **输出发布**：`reports/feed.xml` (RSS) + GitHub Pages，也可生成 HTML 报告或
  推送回 Zotero。

调度：**每天** `cron: "5 22 * * *"`（北京 06:05），外加 `push` 到 `main` / `codex/dev` 触发。

上游打分配置（`875591d:config/scoring.yaml` 原文）：

```yaml
weights:
  similarity: 0.45   recency: 0.15   citations: 0.15   altmetric: 0.10
  journal_quality: 0.04   author_bonus: 0.02   venue_bonus: 0.04   # 和 = 0.95
thresholds:
  must_read: 0.75   consider: 0.5
decay_days:
  fast: 3   medium: 7   slow: 30      # 阶梯衰减
whitelist_authors: []  whitelist_venues: []
```

### 2.3 上游隐含的四个假设，全被推翻

这是理解后续所有改造的钥匙。上游是个**通用**工具，面向任意研究者；
我们的用户是一个**特定**博士课题，两者的假设差距就是改造量的来源。

| 上游假设 | 实际情况 | 后果 |
|---|---|---|
| Zotero Web API 能看到文库 | 4399 篇里只有 **513 篇**同步过（实测 SQL） | 画像只基于 **11.7%** 的阅读量 |
| 每天推一次合适 | 用户要的是每周一次的"周报" | 每天一封 = 噪声 |
| 分数只需内部排序可比 | 阈值 `0.75 / 0.5` 被当成绝对值用 | 权重和 0.95、分量未加界 → 阈值无意义 |
| "相关"= 语义相似 | 相似≠同一研究链（陶瓷装甲、表征论文都很"相似"） | 需要显式的主题门和研究链判据 |

## 4. 改造的设计思路（逐条：问题 → 设计 → 代价）

### 4.1 画像来源：Web API → 本地 sqlite + draft release 分发

**问题**：Zotero Web API 只返回 `version > 0` 的条目，即同步到 zotero.org 的。
实测 4399 篇里 513 篇同步、3878 篇本地。用 API 建画像等于只看 11.7% 的阅读量。

**设计**：`src/zotero_local.py` 直接读 `zotero.sqlite`。Zotero 运行时持独占锁，
所以**先复制再读**，只读打开。排除 note / attachment / annotation、回收站、无标题条目。

分发走 **GitHub draft release 资产**：本地 `python -m src.cli profile --local --bundle`
打出 27 MB tar.gz 上传；工作流下载、校验 `embedding_signature` 与当前
`config/embedding.yaml` 一致，不一致**直接 fail**（向量来自不同模型不可比）。

**为什么用 draft release**：draft 的资产需要仓库写权限才能下载，公开仓库也不会泄露
文库内容；而 Actions cache 会过期、artifact 90 天失效。

**代价**：这是**人工步骤**。改了方向定义或嵌入配置就必须重建上传。
工作流只校验嵌入签名、**不校验方向定义**——这是目前最大的隐患，见 §7.1。

### 4.2 嵌入：复用用户已有的远程 encoder，不下本地模型

**问题**：CI 里跑 sentence-transformers 要下载模型、装 torch，慢且脆。

**设计**：`src/vectorizer.py` 拆成 `RemoteVectorizer`（OpenAI 兼容 `/embeddings`）
和 `LocalVectorizer`，`build_vectorizer()` 在没有 key 时回退本地。
实际用 SiliconFlow 的 `Qwen/Qwen3-Embedding-8B`，`dimensions: 1024`
（Matryoshka 截断，原生 4096）。

嵌入按 `(模型签名, Zotero item version)` 缓存在 `profile.sqlite`，所以重建画像时
**只有变动条目重新嵌入**。实测最近一次重建：4399 篇里只嵌了 4 篇，4395 篇复用缓存。

**注意**：只有 *encoder* 可复用，用户其他 Zotero MCP 工具的**索引不可复用**——
候选论文不在任何本地索引里、它们是 chunk 级而这里是 paper 级、模型不同、
CI 也访问不到本地路径。

### 4.3 打分：所有分量钳到 [0,1]，权重和 = 1.0

**问题**（上游遗留）：`citations` 用未加界的 `log1p(c)`。一篇半相关的 2000 引用
老论文得 1.05，压过一篇完全对口的新论文 0.79——对一个**推新论文**的产品，方向反了。
而且权重和 0.95，阈值 `must_read: 0.75` 没有可解释的含义。

**设计**：每个分量显式钳到 [0,1]，权重和严格 = 1.0，因此总分也在 [0,1]，
**阈值跨运行可比**。`src/check_config.py` 校验权重和。

| 分量 | 上游 | 现在 | 形式 |
|---|---|---|---|
| similarity | 0.45 | **0.68** | 见下——不是「0.68 全给最近邻均值」 |
| recency | 0.15 | 0.12 | `exp(-ln2·days/21)` 连续衰减（原来是 3/7/30 阶梯） |
| citations | 0.15 | 0.08 | `log1p(c)/log1p(50)` 饱和 |
| journal_quality | 0.04 | 0.06 | SJR 对数映射，未知刊 0.25（不再与顶刊同分） |
| venue_bonus | 0.04 | 0.04 | 白名单 |
| altmetric | 0.10 | 0.02 | 饱和于 100 |
| author_bonus | 0.02 | **0.00** | 作者信号改走"作者动向"独立频道，不进分数 |

> **2026-09-19 更正 ①：`similarity` 那 0.68 不是全给最近邻均值。** 实际是
> `0.68 × (0.4×最近 5 篇余弦均值 + 0.6×最佳方向质心相似度)`，
> 也就是 **`0.272×最近邻 + 0.408×方向质心`**。所以「是不是等于只按相似度排」这个问题，
> 我连公式都没描述对；方向质心的权重其实比最近邻高。
>
> **更正 ②：把 `author_bonus` 权重设成 0 并没有真的把作者信号挡在排序之外。**
> `config/authors.yaml` 的 `score_bonus: 0.03` 和 `config/citations.yaml` 的 `0.06`
> 是**另一条加分路径**，在有界求和**和倍率之后**才加回，总分到 1.09，叠反馈到 1.17。
> 而 `must_read=0.70` 是按 [0,1] 分布标定的绝对阈值，越界等于**悄悄把阈值放松了**：
> 一篇关注作者的论文实际在 0.67 就被提为必读。两条路径现已都只记录、不计分，并加最终钳制。

阈值按**实测分布**重标，不是拍的：`p50=0.522 p75=0.602 p90=0.655 p99=0.713 max=0.774`
→ `must_read=0.70`（≈p99，选出约 3%）、`consider=0.52`（≈中位数）。
原来的 `consider=0.45` 放进了 76% 的候选，几乎不携带信息。
每次运行都打印 `Score distribution over N ranked works`，换嵌入模型后要重标。

### 4.4 主题门：三层 + 一条受约束的语义旁路

**问题**："语义相似"不等于"同一研究链"。文库里约 247 篇陶瓷装甲会把质心往陶瓷拉；
LPBF TC4 的表征论文和力学论文在嵌入空间里非常近。

**设计**（`src/fetch_new.py::_filter_by_topic`，顺序执行）：

1. **`exclude_keywords` 否决**（标题+摘要）。**用定向短语，不用裸词**：
   `ceramic armor` / `ceramic matrix composite` / `SiCf` 而不是裸 `ceramic`——
   后者会误杀"带陶瓷涂层的 TC4 动态断裂"这类真正相关的论文。
2. **`required_any_group_sets`**：组内 AND，组间 OR。
   典型一条 = 「金属 AND 温度/率/状态词 AND 力学词」。
3. **`include_keywords` 粗兜底**（`require_topic_match: true` 时至少命中一条）。

**语义旁路**：`semantic_facets`（方向语义检索命中）或引文网络命中可跳过第 2 层。
这是**跨圈发现**的设计意图——关键词列表写不出来的措辞要靠语义找。
但旁路现在**受一个力学锚点约束**（`mechanics_anchor_keywords`），理由见 §5 缺陷 #3。

### 4.5 研究方向：11 个 facet，按研究链切分而非按聚类形状

**问题**：早期把方向总结成 7 个，用户指出"我的研究方向可不只你说的那几个……特别你说
的率温耦合有失偏颇，不耦合的我也研究"。核对发现 406 个配置关键词里 329 个未被覆盖。

**设计**：方向**按研究链分段**（材料 / 温度 / 应变率 / 应力状态 / 硬化 / 断裂 /
损伤 / 标定 / 子程序 / 冲击验证 / 其他金属同链），而不是按 k-means 的自然形状。
聚类只用来**取术语**（保证与文库实际用词一致）和**核对覆盖**。

关键决策：**温度与应变率必须拆开**。对 4399 篇做 k-means 时，高温本构与 SHPB 应变率
各自独立成类，印证了用户的说法。

另一个：**"其他金属的同链研究"与 TC4 核心同为 ×1.0**，不是"降级的借鉴"。用户原话：
只要同样在做温度/率/应力状态下的塑性、断裂、损伤，并走到标定、子程序、侵彻验证，
不是钛合金也同样值得读；区别只在参数不能直接套用，不在价值高低。

每个 facet 带 `use`（怎么用）和 `verify`（核对什么）两个字段，直接渲染进报告的
"迁移卡片"。

### 4.6 研究优先级倍率：first-match-wins，**顺序即语义**

`config/scoring.yaml::research_priorities` 自上而下，第一条命中决定倍率：

| # | 规则 | 倍率 | 匹配范围 |
|---|---|---|---|
| 1 | TC4核心研究 | 1.00 | 标题+摘要 |
| 2 | 外围方法参考 | 0.70 | **仅标题** |
| 3 | 跨金属方法参考（反演/数值实现） | 1.00 | 标题+摘要 |
| 4 | 跨金属方法参考（其他金属本构/断裂） | 1.00 | 标题+摘要 |
| 5 | 表征主导 | 0.55 | **仅标题** |
| 6 | 机制参考 | 0.85 | 标题+摘要 |
| — | 其他相关研究（兜底） | 0.90 | — |

两条约束，都有事故来源（见 §5 #15、#16）：

- **「外围方法参考」不能排最顶上**：曾经在第一位，结果
  `Ductile fracture of coated Ti-6Al-4V under dynamic loading` 因为标题有 "coated"
  被降 30%。现在 TC4核心研究 永远在它前面。
- **但也不能排在「跨金属」后面**：那样它对该管的论文**一次都不会生效**。

**为什么「表征主导」只看标题**：正经论文在断口分析里用 EBSD 完全正常，不该因此降权；
标题就叫 `EBSD characterization of ...` 的，研究对象就是表征本身。
**门决定"是不是研究我的材料"，标题决定"是不是以表征为主"——两个判断分开做。**

`src/check_config.py` 校验倍率**在同一 match 范围内**非递增。跨范围不比较：
仅看标题的规则读的是标题+摘要规则所读文本的**真子集**，把低倍率标题规则放在高倍率
标题+摘要规则之前是**刻意收窄**，不是遮蔽。

### 4.7 去重：子集陷阱

**问题**（上游遗留）：用 rapidfuzz `token_set_ratio`。该算法对**严格子集**给 100 分，
于是文库里一篇会议摘要会把同名期刊全文顶掉——**静默丢论文**，无日志。

**设计**：改 `token_sort_ratio` + 长度比守卫 `MIN_LENGTH_RATIO = 0.75`，
且每次抑制都打 INFO 日志。

### 4.8 交付历史与幂等

**问题**（上游遗留）：`push:` 触发会跑全流程。一天正常开发提交几次，就发几封"周报"、
把 API 预算烧几遍，**最糟的是把那些论文标记成已推送**，于是它们再也不会出现在真正的
周四推送里。

**设计**：删掉 `push` 触发，代码变更由独立的 `ci.yml` 验证。
`data/watch-state/state.json` **提交回仓库**（不是 artifact——artifact 90 天过期，
丢了历史就是重复推送）。`--defer-history`：先发布、后记账，发送失败不会误标已送。

### 4.9 中文化：一次调用出三样，按内容哈希缓存

`src/enrich_zh.py` 一次 chat 调用同时产出**中文标题 + 一句话结论(TLDR) + 全文摘要翻译**，
按 `sha256(title\0abstract)[:16]` 缓存。

两个坑：Qwen3 默认输出长推理链，会撑爆超时并埋掉 JSON → 必须 `enable_thinking: False`；
以及 `response_format: json_object` 需要 `{"items":[...]}` 包一层。

**失败降级是分级的**（这是被两次事故逼出来的，见 §5 #17、#18）：
整批失败 → **拆半重试**而不是原样重发；多项批次只给 1 次尝试（超时是确定性的，
重试必然再撞同一堵墙）；拆到单篇才给满重试预算。最坏情况从"整批 8 篇全丢"变成
"丢一篇"。缓存随交付历史提交回仓库，下周自动补上这次丢的。

### 4.10 两个输出面，职责不同

- **网页周报**（`src/report_html.py`）＝**阅读面**。三栏（276px / 1fr / 292px，
  最大 1780px），完整摘要 + 中译（**默认显示英文原文**，"翻译"按钮切换）、
  按序位分配的方向色标、往期、作者动向、运行诊断。视觉语言照抄 OpenScholar 的实测 CSS。
- **邮件**（`src/digest_email.py`）＝**通知面，不是周报的复制品**。
  **全部论文都在**，但必读 3 行（英文标题 / 中文标题 / 一句话结论），其余每篇 **1 行**。
  标签、作者、期刊、日期、相关度分数**一律不进邮件**——它们重复了分区标题、每篇多占
  一行、且让视觉焦点消失。

  邮件客户端会剥 `<style>`、丢 `<svg>`、把 `<details>` 永远展开 → 全部内联样式 + table 布局。
  `position:sticky` 也只在元素比视口矮时才有空间生效（网页侧的坑）。

### 4.11 三个独立频道：不进主排序，各自成块

- **作者动向**（`src/author_watch.py`）：关注作者的新作 + **查漏补缺**（你可能没留意
  的作者）+ **新涌现**（45 天内首次出现），带单位、样例论文和一个预填的
  "加入关注" issue 链接。
- **引文发现**（`src/citation_watch.py`）：种子论文的引用/被引、合作者网络。
- **版本监控**（`src/version_watch.py`）：预印本 → 正式发表、撤稿、更正。

这三个不参与主分数（所以 `author_bonus` 权重归 0），避免"作者有名"污染相关度。

### 4.12 预算与可靠性

`src/network_budget.py`：按域名计数，接近上限时**为版本检查留出配额**；
期刊/查询列表**轮转**（`iter_rotation`）保证长期覆盖而不是每次都打前几个。
`src/http_utils.py::request_with_retry` 统一退避重试。
检索检查点存 cache，失败也保存（`if: always()`）。

### 4.13 验证工具（本轮新增，都是常驻的）

**这一条是我认为最重要的改造**。之前整个仓库**零测试**，所有判断靠看输出。

- `src/check_config.py`：权重和、阈值序、倍率序、嵌入配置。
- `tools/check_topic_gate.py`：**用真实匹配代码重放两个集合，量化召回与精度**。
  召回集 = 用户 4399 篇文库（本来就全在题）；精度集 = 标注的离题标题；
  守卫集 = 必须留下的在题标题。支持 `--compare HEAD` 做改动前后对比。
- `tools/preview_report.py`：用 fixture 秒级渲染网页 + 邮件，排版迭代不用跑全流程。
- `tools/discover_facets.py`：对文库向量做 spherical k-means，用于核对方向覆盖。
- 14 个测试文件，132 个用例。

## 5. 缺陷清单

分两类：**[上游]** = `Yorks0n/ZotWatch` 原实现就有、跑真实数据才暴露；
**[本轮]** = 阶段 ③ 改造自己引入又修掉的。

### 5.1 上游遗留（12 个）

| # | 问题 | 后果 |
|---|---|---|
| 1 | `citations` 项未加界（`log1p(c)` 无上界） | 2000 引用的半相关老论文（1.05）压过对口新论文（0.79） |
| 2 | 权重和 = 0.95，分量未钳 | 阈值 `0.75/0.5` 没有可解释含义，跨运行不可比 |
| 3 | 去重用 `token_set_ratio` | 严格子集得 100，库里一篇会议摘要顶掉期刊全文，**静默丢论文** |
| 4 | Zotero Web API 建画像 | 只看到 **11.7%** 的文库 |
| 5 | `push:` 触发跑全流程 | 每次提交发一封"周报"，并把论文标记为已推送 → 真正的周四推送里消失 |
| 6 | 相似度只取最近 1 篇 | 单篇噪声主导相关度 |
| 7 | 时间衰减是 3/7/30 阶梯 | 第 4 天和第 7 天断崖 |
| 8 | 未知期刊与顶刊同分 | 无 SJR 记录的刊白捡分 |
| 9 | 交付历史存 artifact | 90 天过期，过期即重复推送 |
| 10 | `FaissIndex.save()` 不建父目录 | 只因工作流先 `mkdir -p data` 才没炸 |
| 11 | Crossref `date-parts` 可能只有年 | 存成 YYYY-01-01，全显示成"2026"而非真实日期 |
| 12 | 语义命中无条件跳过主题门 | 见下 |

**#12 值得展开**，它是"表征论文泛滥"的根因，三个机制叠加：
`_fetch_semantic` 给**每一条**语义结果打 `semantic_facets`；`_filter_by_topic` 把这个
标记当成"已验证相关"直接放行；而方向的 `semantic_query` 是**一句话**，OpenAlex 按
句子找近邻——`lpbf_tc4` 当时那句写的是
`"microstructure, porosity, lack of fusion, build orientation, heat treatment"`，
一句纯表征的话，它的近邻就是表征论文，且**完全跳过关键词检查**。
`problem_ranking.py` 还专门给低引用的语义发现留了探索位，等于优先推新的表征论文。

### 5.2 本轮改造暴露/引入（10 个）

| # | 类型 | 问题 | 后果 |
|---|---|---|---|
| 13 | 配置 | 主题门拿套话当力学证据 | `mechanical properties` 等 5 个词，在 4399 篇里有 **96 篇（2.2%）**只有套话、没有任何真力学术语 |
| 14 | 配置 | `&research_metals` 含裸词 `alloy` | `alloy + cryogenic + hardening` 放进原子尺度 HEA |
| 15 | 配置 | `Materials Characterization` 在追踪期刊里 | 每周爬最多 5 页，源源不断喂表征论文 |
| 16 | 配置 | 降权规则排在 ×1.0 规则之后 | **对该管的论文一次都没生效过**（见下） |
| 17 | 代码 | 翻译整批超时即整批丢弃 | 27 篇里 8 篇无中文，卡片残缺不齐 |
| 18 | 代码 | `zh-cache.json` 不跨运行保存 | 每次 `0 cached`，重复付费，失败永远补不回来 |
| 19 | 代码 | 方向色相用哈希 | 7 个方向 8 个颜色只得到 5 个色相 |
| 20 | 代码 | 摘要从中间截断（`petalling at lo`） | 按词边界切，中日韩回退 |
| 21 | 代码 | 邮件里一行永不闭合的 `<table><tr><td>` | 靠客户端容错 |
| 22 | 产品 | 邮件把整期塞进去 | 信息过载，无重点 |

**#16 值得展开**——这是"顺序即语义"的典型事故。降权规则写好了却从没生效：
涂层（Cr2AlC on H13 steel）、热变形（AA3102、近α钛）都被「金属 + constitutive」
以 ×1.0 先认走；腐蚀那篇（Ti/CeO2）更隐蔽，被「反演/数值实现」用 `fracture energy`
认走——那个词在方法规则里本意是**数值正则化参数**（配 `characteristic length`、
`nonlocal damage`），这篇里却是**材料韧性**。关键词无法消歧，只能靠顺序。

**#17 值得展开**——超时是**确定性**的，不是运气差：提示词要求每篇翻译全文摘要，
8 篇一批 = `max_tokens 7712`，摘要一长就跑不完 180 秒。而
`request_with_retry` 把**同一个超大请求**原样重发两次，必然再撞同一堵墙，
三次 180 秒全部白等（占该次运行 24 分钟里的 9 分钟）。

### 5.3 改动效果（实测，非估计）

> **2026-09-19 更正。** 本节原先写的是「4/10 → 8/10、语义 0/10 → 7/10、
> 文库**召回** 70.3% → 69.1%」，并称工具"用真实匹配代码重放"。两处都不成立：
> 工具当时**自己复制了一份判定逻辑**（缺撤稿过滤、条目类型过滤、作者/引文路径），
> 而 `--compare` 只换配置不换代码，把代码改动算到了配置头上。
> 下面是修好工具之后重测的数字，两侧的 `src/` 和 `config/` 都按版本钉死。
> 方向没错，数字不对——而且**那三个指标的名字也是错的**，见下。

`python tools/check_topic_gate.py --compare 24cacf4`（过滤改动之前的提交）：

```
off_blocked            5/11  →  9/11
  其中走语义路径的      1/11  →  8/11
guards_kept             6/6      6/6
library_kept           70.2%  → 69.1%
```

**这三个指标不叫精度和召回**，原先那样叫是错的：

- `library_kept` —— 文库保留率，是**回归信号**，不是召回。「整个文库按定义全部在题」
  和本文档自己承认的「库里约 247 篇陶瓷装甲 + 离题表征论文」直接矛盾，那些本来就该被拒。
  突然下跌说明改动砍深了，仅此而已。
- `off_blocked` —— 11 条手挑负例上的拒绝率，不是精度。反复拿同一批负例调规则会过拟合。
  它只回答「我这次要修的那件事修好了吗」。
- `guards_kept` —— 收紧过头的护栏，必须满分。

真正的基准需要人工标注样本，口径和流程见 `tests/fixtures/benchmark.md`，
工具是 `tools/benchmark_gate.py`。**目前尚未标注**，因为标注要本人判断——
我对「这篇算可迁移还是机制参考」的判断，正是要被检验的东西。

重建画像后 `lpbf_tc4` 方向从 **436 篇降到 368 篇**——68 篇只靠 EBSD / 织构 /
热处理挂进来的论文不再参与该方向质心。

对 2026-09-19 试跑的 27 篇真实论文重新打分：5 篇落到「外围方法参考 ×0.70」
（AA3102 热变形、近α钛热变形、Cr2AlC 涂层、Ti/CeO2 腐蚀、CFRP 管），
2 篇落到「表征主导 ×0.55」，**27 篇里没有一篇标题带 EBSD / TEM / SEM / XRD**。

## 7. 尚未解决（按我认为的优先级排序）

1. **【最高】画像包与方向定义会漂移。** 工作流只校验 `embedding_signature`，
   改了 `config/research.yaml` 的 `terms` / `name` **不会**触发校验失败，
   线上会悄悄用旧质心。今天要不是手动重建上传，过滤改动有一半白改。
   **应该把方向定义也纳入签名。**
2. **核心材料覆盖不足。** 2026-09-19 那期 `增材 TC4 缺陷与力学响应` 只出了 2 篇，
   且**都不是 TC4**（Ti/CeO2 复合、FFF 316L 钢）。是召回不够，还是本周确实没有？
   现有诊断分不清。
3. ~~**主题门召回 69.1%，剩下 30.9% 是什么没查过。**~~ **部分已查明（2026-09-19）**：
   按「门的判定 × 有无摘要」分层，被拒的 1359 条里 **418 条（31%）根本没有摘要**——
   关键词组需要文本证据，没摘要就只剩标题，匹配不上是必然而非误杀。剩下 941 条有摘要
   却被拒的，才是真正需要人工标注判断的部分。分层数据由 `tools/benchmark_gate.py --sample`
   产出。原文如下：有多少是书章节/学位论文/无摘要
   条目，有多少是真被误杀？
4. **`research_priorities` 靠人肉排序维持语义正确**，规则一多就出 #16 那种事故。
   有没有更不容易错的表达方式（比如显式 priority 字段 + 冲突检测）？
5. **板料成形该不该降权？** 现在 ×1.0。用户的屈服准则/断裂轨迹研究
   （Barlat / Yld2000 / Hill48 / FLD）本来就出自板料成形圈，一刀切会伤核心；
   但"马氏体钢回弹预测"这种纯成形应用价值确实低。暂不动。
6. **`neighbors=5` 是拍的**，没做敏感性分析。
7. **单次运行 12–24 分钟，方差大**，主要在网络 I/O。没有分段计时。

## 8. 请特别挑战的假设

1. 用"关键词组 + 受约束语义旁路"做主题门，而不是训一个分类器——在**只有一个用户、
   没有标注数据**的前提下，这个选择对吗？有没有更省心的做法？
2. `first-match-wins` 的倍率表用**顺序编码语义**——已经出过 #16 这一次事故。
   这个结构是不是本身就有问题？
3. similarity 权重 0.68 压倒性，其余五项加起来 0.32——**实际上是不是等于只按相似度排**？
   如果是，那另外五项是不是自欺欺人？
4. 画像走"本地构建 + release 资产"这条人工链路，可靠性和可维护性如何？
   有没有既能覆盖全库、又不需要人工步骤的方案？
5. 每周一封邮件 + 一个网页，是不是正确的产品形态？
6. 第 5 节 22 个缺陷里，**上游 12 个、本轮 10 个**。从这个故障模式分布看，
   你觉得**还有哪些同类问题没被发现**？这是我最想听的。
