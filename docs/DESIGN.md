# ZotWatch 设计说明（供外部审阅）

> 目的：把当前实现的设计意图、关键取舍和已知缺陷一次讲清楚，便于第三方review。
> 状态：2026-09-19。以 `main` 分支为准。凡文中给出的数字都是实测值，不是估计。

---

## 0. 一句话

ZotWatch 每周一次，从用户的 Zotero 文库（4399 篇）学出研究兴趣画像，
去 OpenAlex / Crossref 抓最近 30 天的新论文，按"与本人研究链的相关度"排序，
产出一个网页周报 + 一封邮件简报，跑在 GitHub Actions 上，无服务器。

用户的研究链（这是全系统的判据，反复出现）：

```
材料 (LPBF/SLM TC4) → 载荷条件 (温度 / 应变率 / 复杂应力状态)
                    → 现象 (塑性变形 / 延性断裂 / 损伤演化)
                    → 模型 (本构与失效模型的建立与标定)
                    → 实现 (UMAT/VUMAT, LS-DYNA/Abaqus)
                    → 验证 (冲击侵彻试验)
```

## 1. 端到端数据流

```
                      ┌─ 本地（人工，配置变更时才跑）────────────────┐
                      │  zotero.sqlite (4399 篇)                      │
                      │      ↓ src/zotero_local.py  只读副本          │
                      │  嵌入 (SiliconFlow Qwen3-Embedding-8B, 1024d) │
                      │      ↓ src/build_profile.py                   │
                      │  profile.sqlite + faiss.index + profile.json  │
                      │      ↓ tar.gz → GitHub draft release 资产     │
                      └───────────────────────────────────────────────┘
                                      ↓ 每周四 16:35 (北京)
┌─ GitHub Actions ─────────────────────────────────────────────────────┐
│ 1. 下载画像包，校验 embedding_signature 与 config 一致，否则直接失败 │
│ 2. 召回   src/fetch_new.py                                           │
│      ├ 期刊追踪 (Crossref, 按 ISSN/刊名轮转)                         │
│      ├ 关键词查询 (~190 条, OpenAlex + Crossref)                     │
│      ├ 语义检索 (每个方向一句 semantic_query → OpenAlex)             │
│      └ 引文网络 (src/citation_watch.py: 引用种子/被引/合作者)        │
│ 3. 主题门 _filter_by_topic  ← 三层，见 §4                            │
│ 4. 去重   src/dedupe.py  (与文库比对 + 批内互比)                     │
│ 5. 打分   src/score_rank.py  ← 有界加权，见 §3                       │
│ 6. 多样性选取 src/problem_ranking.py (每方向配额 + 探索位)           │
│ 7. 中文化 src/enrich_zh.py (中文标题 + 一句话结论 + 全文摘要翻译)    │
│ 8. 出稿   src/report_html.py (网页) + src/digest_email.py (邮件)     │
│ 9. 发布   GitHub Pages + SMTP + RSS                                  │
│10. 记账   data/watch-state/state.json (已推送) 提交回仓库            │
└──────────────────────────────────────────────────────────────────────┘
```

单次运行实测 12–24 分钟。

## 2. 为什么画像在本地建、用 release 资产分发

**Zotero Web API 只返回同步到 zotero.org 的条目**。实测：4399 篇里只有 513 篇
同步过，3878 篇是本地条目。用 Web API 建画像等于只看到 12% 的阅读量。

所以画像在本地从 `zotero.sqlite` 建（只读副本，Zotero 运行时持锁），打成 27 MB
的 tar.gz 传到 draft release。draft release 的资产需要写权限才能下载，因此不会
公开泄露文库内容。

**代价 / 风险**：这是人工步骤。改了 `config/research.yaml` 的方向定义或
`config/embedding.yaml` 之后必须重建上传，否则线上用的是旧质心。
工作流只校验 `embedding_signature`，**不校验方向内容**——这是一个已知缺口（§7）。

## 3. 打分模型

`config/scoring.yaml`：

| 分量 | 权重 | 说明 |
|---|---|---|
| similarity | 0.68 | 与文库最近 5 篇的余弦相似度均值（FAISS `IndexFlatIP`，单位向量） |
| recency | 0.12 | `exp(-ln2 · days / 21)`，连续衰减而非阶梯 |
| citations | 0.08 | `log1p(c)/log1p(50)`，饱和 |
| journal_quality | 0.06 | SJR 对数映射，未知刊给 0.25 |
| venue_bonus | 0.04 | 白名单期刊 |
| altmetric | 0.02 | 饱和于 100 |

**核心约束：每个分量都钳到 [0,1]，权重和 = 1.0，所以总分也在 [0,1]，
阈值跨运行可比。** 这条是被一个真实缺陷逼出来的：原先 citations 用未加界的
`log1p(c)`，一篇半相关的 2000 引用老论文得 1.05，压过一篇完全对口的新论文 0.79
——对一个"推新论文"的产品来说方向正好反了。

阈值按实测分布定，不是拍的：`p50=0.522 p75=0.602 p90=0.655 p99=0.713 max=0.774`，
取 `must_read=0.70`（≈p99，选出约 3%）、`consider=0.52`（≈中位数）。
每次运行都会打印 `Score distribution over N ranked works`，改嵌入模型后要重标。

最后乘一个 **研究优先级倍率**（`research_priorities`，见 §5）。

## 4. 主题门：三层过滤

`src/fetch_new.py::_filter_by_topic`，顺序执行：

1. **`exclude_keywords` 否决**（标题+摘要）。用定向短语而非裸词：
   `ceramic armor` / `ceramic matrix composite` / `SiCf` 而不是裸 `ceramic`，
   因为后者会误杀"带陶瓷涂层的 TC4 动态断裂"这类真正相关的论文。
2. **`required_any_group_sets` 关键词组**。每个 group set 内部是 AND，
   set 之间是 OR。例如「金属 AND 温度/率/状态词 AND 力学词」。
3. **`include_keywords` 粗兜底**（`require_topic_match: true` 时至少命中一条）。

**旁路**：语义检索命中（`semantic_facets`）或引文网络命中可以跳过第 2 层——
这是"跨圈发现"的设计意图，关键词列表写不出来的措辞要靠语义找。

> **2026-09-19 修复**：旁路原先是无条件的，且 `_fetch_semantic` 会给**每一条**
> 语义结果打 `semantic_facets`。而方向的 `semantic_query` 是一句话，OpenAlex 按
> 句子找近邻——`lpbf_tc4` 当时那句写的是 "microstructure, porosity, lack of
> fusion, build orientation, heat treatment"，一句纯表征的话，它的近邻就是表征
> 论文，且**完全跳过关键词检查**。现在语义命中仍可跳过关键词组，但必须先命中
> `mechanics_anchor_keywords`（本构/塑性/断裂/损伤/应变率/侵彻/UMAT…）；命中不了
> 不是被拒，只是失去特权，回去走正常的门。

## 5. 研究优先级倍率：first-match-wins，顺序即语义

`config/scoring.yaml::research_priorities` 自上而下匹配，**第一条命中的决定倍率**。
当前顺序：

| # | 规则 | 倍率 | 匹配范围 |
|---|---|---|---|
| 1 | TC4核心研究 | 1.00 | 标题+摘要 |
| 2 | 外围方法参考 | 0.70 | **仅标题** |
| 3 | 跨金属方法参考（反演/数值实现） | 1.00 | 标题+摘要 |
| 4 | 跨金属方法参考（其他金属本构/断裂） | 1.00 | 标题+摘要 |
| 5 | 表征主导 | 0.55 | **仅标题** |
| 6 | 机制参考 | 0.85 | 标题+摘要 |
| — | 其他相关研究（兜底） | 0.90 | — |

两条设计约束，都有血泪来源：

- **「外围方法参考」不能排在最顶上**。它曾经在第一位，结果
  `Ductile fracture of coated Ti-6Al-4V under dynamic loading` 因为标题里有
  "coated" 就被降 30%。现在 TC4核心研究 永远在它前面。
- **但它也不能排在「跨金属」后面**。2026-09-19 试跑发现它对该管的论文一次都没
  生效过：涂层（Cr2AlC on H13 steel）、热变形（AA3102 / 近α钛）都被
  "金属 + constitutive" 以 ×1.0 先认走；腐蚀那篇（Ti/CeO2）更隐蔽，被
  「反演/数值」那条用 `fracture energy` 认走了——那个词在方法规则里本意是数值
  正则化参数（配 `characteristic length`、`nonlocal damage`），这篇里却是材料韧性。
  关键词无法消歧，只能靠顺序。

**为什么「表征主导」只看标题**：一篇正经论文在断口分析里用 EBSD 完全正常，不该
因此降权；标题就叫 `EBSD characterization of ...` 的，研究对象就是表征本身。
**门决定"是不是研究我的材料"，标题决定"是不是以表征为主"，两个判断分开做。**

`src/check_config.py` 校验倍率**在同一 match 范围内**非递增。跨范围不比较，
因为仅看标题的规则读的是标题+摘要规则所读文本的真子集，把一条低倍率的标题规则
放在高倍率的标题+摘要规则之前是刻意收窄，不是遮蔽。

## 6. 两个输出面，职责不同

- **网页周报**（`src/report_html.py`）：阅读面。三栏布局，完整摘要 + 中译（默认
  显示英文原文，"翻译"按钮切换）、方向色标、期刊、往期、作者动向、运行诊断。
- **邮件**（`src/digest_email.py`）：通知面，不是周报的复制品。
  **全部论文都在**，但必读 3 行（英文标题 / 中文标题 / 一句话结论），其余每篇 1 行
  （中文标题）。标签、作者、期刊、日期、相关度分数一律不进邮件——它们重复了
  分区标题、每篇多占一行、且让视觉焦点消失。
  邮件客户端会剥 `<style>`、丢 `<svg>`、把 `<details>` 永远展开，所以全部用内联
  样式 + table 布局。

## 8. 尚未解决 / 特别想听意见的地方

1. **画像包与方向定义会漂移。** 工作流只校验 `embedding_signature`，改了
   `config/research.yaml` 的 `terms` / `name` 不会触发校验失败，线上会悄悄用旧质心。
   应该把方向定义也纳入签名。**这是目前最大的隐患。**
2. **`increments` 方向覆盖不足。** 2026-09-19 那期 `增材 TC4 缺陷与力学响应` 只出了
   2 篇，且都不是 TC4（一篇 Ti/CeO2 复合、一篇 FFF 316L 钢）。核心材料在本期几乎
   没出现。是召回不够，还是本周确实没有新论文？现有诊断分不清。
3. **板料成形该不该降权？** 现在是 ×1.0。理由是用户的屈服准则 / 断裂轨迹研究
   （Barlat / Yld2000 / Hill48 / FLD）本来就出自板料成形圈，一刀切会伤到核心；
   但"马氏体钢回弹预测"这种纯成形应用价值确实低。暂时不动。
4. **相似度用"最近 5 篇均值"。** `neighbors=5` 是拍的，没有做过敏感性分析。
5. **主题门的召回率是 69.1%**（对用户自己的文库）。剩下 30.9% 是什么？
   有多少是老书章节 / 学位论文 / 无摘要条目，有多少是真的被误杀？没查过。
6. **`research_priorities` 靠人肉排序维持语义正确。** 规则一多就容易出 §5 那种
   "根本没生效"的事故。有没有更不容易错的表达方式？

## 9. 怎么验证（不靠感觉）

- `python -m src.check_config` —— 权重和、阈值序、倍率序、嵌入配置。
- `python -m unittest discover -s tests` —— 132 个测试。
- **`python tools/check_topic_gate.py --compare HEAD`** —— 关键工具。
  用真实匹配代码重放两个集合：
  - **召回**：用户 4399 篇文库，本来就全在题，门应该基本都留下；
  - **精度**：一份标注的离题标题集（表征主导 / 陶瓷 / 涂层），应该被拒或降权；
  - **守卫**：一份必须留下的在题集，防止收紧过头。

  2026-09-19 这次改动的实测（对比 HEAD）：

  ```
  离题被拦              4/10 → 8/10
    其中走语义路径的    0/10 → 7/10
  在题守卫保住            6/6 → 6/6
  文库召回              70.3% → 69.1%
  ```

- `python tools/preview_report.py` —— 用 fixture 渲染网页 + 邮件，秒级迭代排版。
- `gh workflow run daily_watch.yml -f dry_run=true` —— 真实数据全流程，但不发邮件、
  不发布 Pages、不记交付历史。产物在 artifact 里。**改过滤规则后应该先跑这个**，
  否则一旦过滤还不对，论文被标记成已推送就再也不会出现在下周的正式推送里。

## 10. 配置文件清单

| 文件 | 管什么 |
|---|---|
| `config/research.yaml` | 11 个研究方向：`semantic_query` / `terms` / `use` / `verify` |
| `config/sources.yaml` | 追踪期刊、~190 条查询、主题门三层、力学锚点 |

| `config/translation.yaml` | 中文化模型、批大小、超时 |
| `config/authors.yaml` / `citations.yaml` / `feedback.yaml` / `network.yaml` / `zotero.yaml` | 作者追踪 / 引文发现 / 反馈 / 预算 / Zotero 路径 |

方向定义的依据是用户 2026-09-19 的原话，**不是**从文库聚类反推的：
聚类只用来取术语（保证与文库实际用词一致）和核对覆盖。

## 11. 审阅时特别值得挑战的假设

1. 用"关键词组 + 语义旁路"做主题门，而不是训一个分类器——在只有一个用户、
   没有标注数据的前提下，这个选择对吗？
2. `first-match-wins` 的倍率规则表，用顺序编码语义——§5 已经出过一次事故，
   这个结构是不是本身就有问题？
3. 相似度权重 0.68 压倒性，其余五项加起来 0.32——实际上是不是等于只按相似度排？
4. 每周一封邮件 + 一个网页，是不是正确的产品形态？
